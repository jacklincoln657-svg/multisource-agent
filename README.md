# 多源数据融合的个人效率助手

个人数字生活正分散在 Steam、B 站、飞书、网页等互不相通的平台上：接口不同、字段不同、权限模型也不同。直接把大模型「接到所有 API」上，往往会出现工具选错、长文本撑爆上下文、以及误搜网页、误写日程等问题。

本项目是一个运行在本地的 **多源个人 Agent**：用统一的工具层接入异构数据源，让模型按用户意图选择该查哪里、怎么整理、何时写入外部系统。产品入口是本地 Web 对话界面；飞书作为外部工作台参与读写，而不是替代主聊天通道。

当前主要覆盖两个方向：

1. **生活痕迹洞察** — 汇聚游戏、视频等内容消费轨迹，形成可读摘要，并在需要时生成可视化看板  
2. **近日工作整理与写回** — 从白名单工作群与日程/计划表中提炼待办，**在用户确认后**写回飞书日历或计划表  

### 项目定位（便于快速判断）

| 本项目是 | 本项目目前不是 |
|----------|----------------|
| 面向个人的本地多源助手 | 飞书官方机器人或企业 IM 替代品 |
| 强调路由、上下文与写回可控的 Agent 工程实践 | 多租户企业调度 / 审批中枢 |
| 生活洞察 + 工作落盘的效率闭环 | 视频内容理解或字幕转写产品 |
| 看板为生活线的可选交付形态 | 以出图为唯一目标的演示页 |

界面中的角色人设只影响表达风格，不参与工具选择与业务决策。

## 为什么做

异构数据很难、也不必先「揉成一张总表」。更稳妥的路径是：

> **把差异留在各数据源内部，把选择权交给 Agent。**  
> 每个平台独立完成鉴权与取数，再以统一的 Tool 形态暴露给模型；模型根据任务决定用哪一路、是否需要补证据、是否允许产生外部副作用。

由此形成一条清晰的能力叙事：

**理解意图 → 选择数据源 → 获取并压缩信息 → 按场景交付（对话 / 看板 / 确认后写回）。**

## 怎么做（工程要点）

### 可扩展的数据源接入

各源以插件形式注册：HTTP/鉴权在适配层，`@tool` 与使用说明（SKILL）在插件层，进程启动时统一装载。扩展新平台时，优先增加插件与适配代码，而不是反复改写 Agent 核心提示词。

> 说明：当前为启动时注册；修改插件后需重启。这是有意选择的工程边界，便于推理路径稳定、可预期。

### 长群聊的上下文治理

工作群全文很长。本项目将原文保存在会话缓存中，主对话只消费旁路提炼的「信息卡」，并保留指向原文的锚点；用户追问细节时再按需回捞短切片。这样既控制上下文规模，又避免「摘要之后细节无从核对」。

### 外部调用与写回的约束

- **本站优先**：已接入平台能回答的问题，避免无必要的网页检索  
- **证据可升级**：当本地信息不足、且用户确实需要外部事实时，再进行受控搜索与页面读取，并对单次问题设置调用上限  
- **写回先确认**：日程与计划表写入前需用户确认；OAuth 刷新与批量写入采用加锁、串行等措施，降低凭证竞态与误写风险  
- **读取范围可控**：群聊接入限定在产品配置的白名单会话内  

上述约束的目标很明确：让 Agent「能办事」，同时把成本与副作用关在可解释的闸门之内。

## 正在拓展的方向

当前版本已经跑通「多源接入 → 有组织地取数与整理 → 受控写回」这条底座。下一阶段的目标，是在同一套个人助手上，把能力从**看懂信息、整理信息**，进一步推进到**在数字世界里替用户把事办完**——同时把接入成本降下来，让能力可以随个人兴趣生长。

### 1. 从「收集与整理」到「代劳与闭环」

今天的系统擅长读轨迹、抽待办、确认后写日历；这更接近「参谋」。真正贴近日常效率的下一步，是补齐类似 Manus 所代表的那一类能力：根据用户偏好与当下意图，自主完成订阅、购物、订票等需要多步交互、带外部副作用的任务。

这样做的原因很直接：个人助手如果只能汇总信息，价值会停在「更好看的通知中心」；只有当它能在用户授权与确认策略下，把「我想……」落到「已经帮你办好了」，多源接入才从数据聚合升级为完整的效率闭环。现有的写回闸门、调用预算与确认机制，正是为这类更高风险动作预先打下的约束基础。

### 2. 多 Agent 协作

随着可操作的应用变多、任务从单次查询变成跨应用长链路，单一 Agent 同时承担路由、执行与校验会越来越吃力。拓展中的方向是按职责拆分协作：例如由规划/路由 Agent 理解意图并分派，由领域 Agent 负责具体应用内的操作，再由约束层统一处理确认、预算与失败回收。

在数据源与工具较少时，单 Agent 足够清晰；当「可读的源」变成「可操作的应用矩阵」时，多 Agent 才是为了稳定性与可维护性而引入的结构，而不是为了堆概念。

### 3. 按个人爱好装配应用，并简化拔插

不同用户关心的应用完全不同：有人要内容与游戏，有人要出行与消费，有人要办公协同。理想状态不是把所有平台写死进核心，而是让用户按自己的兴趣启用或添加应用，助手只加载与自己相关的那一套工具。

这也要求接入方式继续简化：从现在「手写适配 + 启动注册插件」的稳健路径，演进到更标准的工具发现与声明（例如朝 OpenAPI / MCP 一类协议靠拢），降低新增一个应用的工程成本，使拔插更接近「声明能力 → 注册 → 按需启用」。底座阶段把异构性隔在插件内，正是为了给这一步留出空间。

> 以上为进行中的产品与工程演进，不等同于当前仓库已全部交付；现网能力仍以「已实现能力」一节为准。工程上会同步补强写回幂等、凭证可观测性与检索质量等底座细节，以支撑更强的自主行动。

## 快速开始

环境：Python 3.11+，以及可用的大模型 API Key（见 `.env.example`）。

```bash
cd cyber_lobster_api_fusion
cp .env.example .env    # 至少配置 DEEPSEEK_API_KEY，其余数据源按需填写
python app.py
```

建议自检：

```bash
python scripts/smoke_plugins.py
python scripts/smoke_feishu.py          # 使用 --write 会写入测试数据，请谨慎
```

若需以个人身份写入飞书日历，请先在飞书开放平台完成应用与权限配置，再运行：

```bash
python scripts/feishu_oauth_login.py
```

授权文件默认保存在 `workspace/feishu_user_token.json`，请勿提交到版本库。Steam、B 站、Tavily、飞书等均为可选能力，未配置时仍可用 Mock 或其它已启用源进行体验。
